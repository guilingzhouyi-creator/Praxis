# CompletionJudge — the 11-dimension "done" gate

Machine verdict on task completion: `scripts/sh/verify-completion.sh` decides
"done", never the agent. Only a `COMPLETE` verdict authorizes declaring a task
finished; the verdict, its per-check flags and numeric metrics are logged to a
shared JSONL and aggregated by `scripts/sh/judge-stats.sh` into
`docs/judge-stats.md`.

## Verdict contract

| Verdict | Meaning | Authorizes "done"? | Exit |
|---|---|---|---|
| `COMPLETE` | All 11 checks **executed** and passed (full mode) | yes — ratchet holds | 0 |
| `PARTIAL` | All **executed** checks passed but ≥ 1 was skipped (fast mode) | **no** — informative only | 0 |
| `INCOMPLETE` | At least one executed check failed; evidence gap printed | no — keep working | 1 |

- A `PASS` never reopens once green (ratchet property: forward only).
- Skipping a check is a deliberate downgrade, never a free pass: a skipped
  verdict is `PARTIAL`, and the dashboard reports it in its own bucket.

## Mode semantics

| Mode | Condition | Recorded as |
|---|---|---|
| `full` | All 11 checks enabled (`--skip` empty, all `COMPLETION_*=1`) | `mode: full`; verdict may be `COMPLETE` or `INCOMPLETE` |
| `fast` | ≥ 1 check skipped (`--skip=tests,coverage`, or `COMPLETION_* = 0`) | `mode: fast`; verdict may be `PARTIAL` or `INCOMPLETE` |

Fast runs exist for cheap push-time auditing (see `push-both.sh`); their
statistics are never mixed with full runs in the dashboard (see Statistics
conventions).

## The 11 checks

| # | Check | Verifier | Pass condition |
|---|---|---|---|
| 1 | Tests | `pytest tests/ -q --tb=short` | full suite green, no early exit |
| 2 | Coverage | `pytest --cov --cov-fail-under` (60, from pyproject) | report ≥ threshold |
| 3 | Net delta | `verify-main-merge-gate.sh main` (three locks) | net ≥ 1000 (or symmetric-deletion / docs-only exemption) |
| 4 | Docs sync | `scripts/py/check_doc_stats.py` | no snapshot drift |
| 5 | Lint/type | `ruff check` + `ruff format --check` + `mypy` | clean |
| 6 | Audit | `pip-audit` | no known dependency CVEs |
| 7 | Complexity | `long_functions` scanner | no function > 200 lines |
| 8 | Import cycle | `scripts/py/import_cycle_check.py` | no cycles |
| 9 | Singleton | `scripts/py/scan_singletons.py` | `conftest.py` `_RESETS` in sync |
| 10 | Changelog | `scripts/py/check_changelog.py` | `[Unreleased]` present and fresh |
| 11 | Doc index | `scripts/py/check_doc_index.py` | every architecture doc linked from README |

Skip switches: `--skip <check,...>` or per-check env (`COMPLETION_TESTS=0`,
`COMPLETION_COVERAGE=0`, … one per check above).

## Logging & aggregation

- Every run appends one JSONL line to the **shared** judge log
  `<main-tree>/.praxis/judge-runs.jsonl` (gitignored runtime data). The path
  is resolved via `git rev-parse --git-common-dir`, so runs from ANY linked
  worktree land in the same file the dashboard aggregates — worktree-local
  logs would go unmeasured. Appends are protected via `flock` to ensure atomic
  writes across parallel worktrees.
- Record schema: `ts` (UTC ISO) / `verdict` / `mode` (`full`|`fast`) /
  `branch` / `duration_s` / `checks` (per-check flags: 0=skipped, 1=pass,
  2=fail) / `metrics` (numeric: `0` when clean, `null` when unmeasured).
- `scripts/sh/judge-stats.sh` aggregates: full vs overall completion rate,
  PARTIAL bucket, failure distribution, per-day trend, per-branch rates,
  per-mode duration avg/P95, longest INCOMPLETE streak, per-check pass rate
  over executed runs, failure pairs, numeric metric series, gate-exemption count.
  All dimensions are available in the `--json`/text local output; **only the
  standards subset enters the committed Markdown dashboard** (see
  "Dashboard inclusion criterion" below).
- `docs/judge-stats.md` is the committed dashboard, regenerated by
  `push-both.sh` on every push — **never hand-edit**.
- Consumers: `push-both.sh` (push-time fast record + dashboard refresh),
  `nightly.yml` (dashboard comparison), agent skills (completion-judge),
  `docs/README.md` (index).

## Statistics conventions

- **Mode split is load-bearing**: full and fast runs are aggregated
  separately (rates, durations, mode counts). The dashboard explicitly displays
  both overall rate and full-mode completion rate (`complete / full_runs`).
  A fast-mode `PARTIAL` is never counted as `COMPLETE`.
- **Zero-metric preservation**: clean runs record `0` (e.g. `tests_failed=0`,
  `ruff_errors=0`, `audit_vulns=0`) rather than `null`, preserving accurate
  baseline averages and minimums in numeric metric trends.
- **Ordering**: records are sorted by `ts`; "latest" metrics follow
  wall-clock order, not log position.
- **Deduplication**: records are deduped on
  `(ts, verdict, branch, duration_s)` — concurrent runs and migrated legacy
  records cannot inflate counts.
- **Legacy records** (pre-`mode` field): mode is derived from check flags
  (any flag 0 or <11 checks ⇒ `fast`).
- **Gate exemptions**: counted per **commit** (`git log --all -z --format=%H%x00%B`),
  never per message line — a subject+body mention counts once.
- **INCOMPLETE framing**: an INCOMPLETE verdict means "machine says not yet"
  — it includes routine accumulation-phase rejections (net delta below
  threshold, changelog stale), not only premature-stop catches.

## Dashboard inclusion criterion (what belongs in the committed dashboard)

The committed `docs/judge-stats.md` is the **quantitative-standard gate
surface** — it carries only metrics that ARE the standard or that PROVE the
standard is enforced (ratchet evidence). Everything else is operator
diagnostics and stays in the `--json`/text output.

**Included (standards + ratchet evidence):**

| Section | Why it qualifies |
|---|---|
| Verdict rates + mode split | the gate's core outcome (is it intercepting?) |
| Failures by check | which standard dimension actually rejects |
| Check pass rate | ratchet evidence — pass once, never reopen |
| Numeric metric series | the quantified standards themselves (coverage ≥ 60, net delta ≥ 1000, mega-functions ≤ 200, ruff 0, audit 0, tests) |
| Daily trend | ratchet direction over time |

**Excluded from the committed dashboard (diagnostics only):**

| Section | Why it does NOT qualify |
|---|---|
| Completion rate by branch | attribution, not a standard — branch names are transient worktree artifacts; small-sample rates (0/1, 0/2) are noise in a committed doc |
| Duration avg/P95 | operational efficiency, not a quality standard |
| Longest INCOMPLETE streak | operational statistic, no threshold semantics |
| Failure pairs | co-occurrence diagnostic, no standard meaning |

Rule of thumb: if a metric has no threshold / ratchet semantics and names a
transient artifact (branch, agent, timestamp), it does not belong in the
committed dashboard.

## Generalization directions (future dimensions)

New dimensions qualify for the committed dashboard only when they carry
threshold / ratchet semantics. Candidate next steps (not yet implemented):

- **Metric monotonicity** — turn each numeric series (coverage_pct,
  mega_funcs, net_delta, ...) into a ratchet check: a run whose metric moves
  against the soft-gate direction (coverage down, mega-functions up) is a
  drift event worth surfacing, mirroring layer_quality.py soft gates.
- **Skip distribution** — which checks are skipped most often in fast mode;
  a frequently-skipped dimension is a blind spot in the standard, i.e. a
  gate-integrity signal with a clear "should be near zero" reading.
- **Exemption trend** — gate exemptions (MERGE_GATE_SKIP) already counted;
  a rising trend is a governance signal (waivers becoming routine).

Explicitly NOT candidates: per-branch / per-agent attribution (no standard
meaning), duration and streak (no threshold), failure pairs (no threshold).
